# UAV 协同排雷模块工作与实现说明

本文只说明协同排雷系统中的无人机部分：无人机如何飞行、规划和避障，如何用 LiDAR 建图并转换成公共地图，如何把传感器观测对齐到 `map` 坐标系，以及如何识别地雷并把地雷的公共坐标交给 UGV。

UGV 的全局导航、近场复定位、机械臂动作和排雷状态机不在本文展开。本文只定义 UAV 最终交给 UGV 的地图和地雷目标接口。

---

## 1. UAV 在协同排雷中的职责

UAV 需要完成五件事：

1. 接收巡检目标或巡检航点，在 PX4 OFFBOARD 模式下稳定飞行；
2. 使用全局 A* 绕开大楼、围墙等大体量障碍，使用 EGO-Planner 处理局部障碍和连续轨迹；
3. 将机载 LiDAR 点云从传感器坐标系转换到稳定地图坐标系，边飞边累积三维地图；
4. 使用下视 RGB-D 相机和地雷实例分割模型识别地雷，把像素检测转换为 `map` 坐标；
5. 向 UGV 发布同一 `map` 坐标系下的地形地图和已融合地雷目标。

完整数据流如下：

```text
                         UAV 飞行链
/uav/goal
    │
    ▼
世界目标→局部目标对齐 → 全局 A* → /goal_elevated → EGO-Planner
                                                   │
前视深度图 → 深度预处理 → EGO 局部占据图 ───────────┘
                                                   │
                                                   ▼
                                          /planning/pos_cmd
                                                   │
                                                   ▼
                                           PX4 Bridge → MAVROS → PX4

                         UAV 建图链
/uav0/velodyne_points_raw
    │
    ▼
格式转换和过滤 → 传感器点云 → 坐标投影 → /points_world
                                            │
                                            ▼
                                      体素累积与清障
                                            │
                         ┌──────────────────┴──────────────────┐
                         ▼                                     ▼
              /points_accumulated                     PCD + 原点 sidecar
                         │                                     │
                         └────────── 地形栅格转换 ──────────────┘
                                           │
                                           ▼
                                  公共 map 下的地形地图

                         UAV 地雷定位链
下视 RGB + 对齐深度 + CameraInfo
    │
    ▼
YOLO 实例分割 → 掩膜内鲁棒深度 → 相机三维点
                                      │
UAV 位姿 + 相机外参 + 同时刻 TF ──────┘
                                      │
                                      ▼
                              map 坐标单帧观测
                                      │
                                      ▼
                           多帧关联、融合和确认
                                      │
                                      ▼
                         地雷目标列表 → 交给 UGV
```

## 3. UAV 载荷、坐标系和话题

### 3.1 UAV 载荷

地雷版 UAV 模型由四部分组成：

| 载荷 | 用途 | 主要参数 |
|---|---|---|
| Iris/PX4 机体 | 飞行动力学和 PX4 SITL | Gazebo Classic + PX4 |
| 前视深度相机 | EGO 局部避障 | 输入 `/iris_depth_camera/camera/depth/image_raw` |
| 360° 16 线 LiDAR | 环境建图和全局 A* | 360×16，3 Hz，0.3～16 m |
| 下视 RGB-D 相机 | 地雷分割和三维定位 | 960×540，8 Hz，约 86° 水平视场，0.05～20 m |

地雷版 SDF 中：

- LiDAR 相对机体位于 `(0, 0, 0.06)`；
- 下视相机模型相对机体位于 `(0, 0, -0.05)`；
- 相机传感器在相机模型内又位于 `(0, 0, -0.02)`；
- 因此相机光心相对 UAV 基座的平移约为 `(0, 0, -0.07)`；
- Gazebo 相机沿本地 `+X` 成像，传感器绕 `Y` 轴旋转 `+90°` 后朝机体 `-Z`，即向下观察。

下视相机话题为：

```text
/mine_camera/rgb/image_raw
/mine_camera/rgb/camera_info
/mine_camera/depth/image_raw
/mine_camera/depth/camera_info
/mine_camera/depth/points
```

图像消息的帧名为：

```text
mine_camera_optical_frame
```

### 3.2 必须使用的坐标系

建议明确区分以下坐标系：

| 坐标系 | 含义 |
|---|---|
| `map` | UAV 最终交付地图和地雷坐标使用的公共坐标系 |
| `world` | Gazebo 世界坐标系；当前启动文件中与 `map` 是单位变换 |
| MAVROS local ENU | PX4 本地坐标，原点通常是 UAV 启动/出生位置，`x` 东、`y` 北、`z` 上 |
| `uav_base_link` | UAV 机体坐标系，避免与 UGV 的 `base_link` 重名 |
| `camera_link` | 前视避障相机安装坐标系 |
| `uav0/velodyne_link` | LiDAR 坐标系 |
| `mine_camera_optical_frame` | 下视相机光学坐标，`z` 为视线前方、`x` 向图像右、`y` 向图像下 |

当前启动文件已经发布：

```text
map -> world                         单位变换
uav_base_link -> camera_link         前视相机外参
uav_base_link -> uav0/velodyne_link  LiDAR 外参
```

地雷在线感知启动文件 `mine_detection.launch` 已正式发布：

```text
uav_base_link -> mine_camera_optical_frame
```

按当前 SDF 的安装关系，使用的光学坐标外参为：

```bash
rosrun tf2_ros static_transform_publisher \
  0 0 -0.07 0.70710678 -0.70710678 0 0 \
  uav_base_link mine_camera_optical_frame
```

其中四元数使相机光学 `+Z` 指向机体 `-Z`。现在不再依赖人工另开 TF 终端；若更换相机安装姿态，必须同时修改 SDF、静态 TF 和标定验证。

## 4. UAV 飞行、全局规划和局部避障

### 4.1 三层职责不能混在一起

当前飞行栈有三层，每层处理的问题不同：

| 层 | 节点 | 负责什么 | 不负责什么 |
|---|---|---|---|
| 全局路径层 | `global_path_planner.py` | 根据累积 LiDAR 地图绕开大楼、墙等大障碍，输出远近合适的子目标 | 不直接控制电机，也不生成高频平滑轨迹 |
| 局部轨迹层 | EGO-Planner | 根据前视深度建立局部占据图，优化连续无碰 B 样条轨迹 | 不擅长在未知大楼群中独自寻找很长的全局绕行路线 |
| 飞控执行层 | `px4_bridge.py` | 把 EGO 的位置指令持续发送给 MAVROS/PX4，负责 OFFBOARD、解锁、起飞和超时悬停 | 默认不重新规划路径 |

因此“无人机避障”不是一个节点完成的，而是：

```text
大范围绕楼：全局 A*
细障碍和轨迹修正：EGO
最终位置设定值执行：PX4 Bridge
```

### 4.2 目标进入系统后的完整流程

合并系统中 UAV 目标话题被单独设为：

```text
/uav/goal
```

这样不会和 UGV 使用的 `/move_base_simple/goal` 冲突。

低空模式下目标链为：

```text
/uav/goal
  → global_path_planner.py
  → /global_path            仅用于 RViz 显示
  → /goal_elevated          当前要追踪的三维子目标
  → waypoint_generator
  → EGO-Planner
  → /planning/pos_cmd
  → px4_bridge.py
  → /mavros/setpoint_position/local
```

高空模式默认不开全局 A*，目标链变为：

```text
/uav/goal
  → goal_elevator.py
  → 把目标 z 固定到 flight_height
  → /goal_elevated
  → EGO-Planner
```

### 4.3 目标坐标如何从公共地图转换到 UAV 局部系

规划器和 PX4 使用 MAVROS local ENU。用户在 RViz 中点击的目标属于公共世界坐标。若 UAV 出生点为：

```text
o = [x_spawn, y_spawn]
```

则目标转换为：

```text
p_local = p_map - o
```

当前 `run_air_ground.sh` 默认：

```text
UAV_X=0.0
UAV_Y=0.0
```

所以 `p_local` 和 `p_map` 数值相同，看不出变换的存在。如果以后把 UAV 改到 `(0, -18)` 等非零出生点，而没有执行上述减法，无人机会整体飞偏一个出生点距离。

启动脚本已经把 `UAV_X/UAV_Y` 传给：

```text
uav_auto_align:=true
uav_align_off_x:=UAV_X
uav_align_off_y:=UAV_Y
```

`global_path_planner.py` 收到目标后执行：

```text
goal_local_x = goal_map_x - offset_x
goal_local_y = goal_map_y - offset_y
```

这里虽然参数名叫 `auto_align`，当前规划器实际优先使用已知出生点固定偏移，不使用可能卡顿的 `/odom` 在线反推值。

### 4.4 全局 A* 如何从 LiDAR 点云得到障碍图

全局规划器输入：

```text
/uav0/mapping/points_accumulated
/mavros/local_position/odom
/uav/goal
```

全局规划器现在读取经过体素融合和射线清障的完整累积点云快照。每次接收快照都重新构建高度图，而不是把历史最高点永久保留。因此 recorder 删除一次拖影或假回波后，对应的全局假障碍也会消失，原来被误封的楼间通道能够重新打开。

它不是直接在三维点云中搜索，而是把点云压成二维高度统计栅格：

1. 栅格分辨率为 `0.5 m`；
2. 范围为 `x,y ∈ [-100, 100) m`，即约 `400×400` 个 cell；
3. 在当前完整快照中统计每个 cell 的最低点 `ground`；
4. 在当前完整快照中统计每个 cell 的最高点 `height`；
5. 用约 `2.0 m` 的局部窗口估计附近地面；
6. 若 `height - local_ground > 1.5 m`，该 cell 先被视为突起；
7. 对突起做连通域分析，只保留占地不小于 `10 m²` 的大障碍；
8. 使用欧氏距离变换计算每个自由 cell 到障碍的真实米制距离；
9. 距离障碍不超过 `1.0 m` 的 cell 作为全局硬障碍；
10. `1.0～1.5 m` 范围只施加小幅软净空代价，不再直接封闭通道。

这套规则的目的如下：

- 大楼、围墙和大棚等大体量结构由全局 A* 绕行；
- 单棵树、细杆等小障碍不把整张全局图堵死，交给 EGO 局部处理；
- 使用“最高点减本地地面”而不是绝对高度，缓坡不会因为海拔升高而被误判成墙；
- 即使 UAV 只扫到楼的上半部分，最高点仍会明显高于本地地面，楼仍能被保留下来。
- 全局层只设置 `1.0 m` 硬净空，前视深度和 EGO 继续负责局部精确避障；
- 软净空代价最大只增加约 12% 单步代价，不会为了追求宽路选择明显更长的路线。

完整点云快照最多按 `1 Hz` 重建一次，给 Gazebo 和 EGO 留出 CPU；规划跟踪定时器仍为 `0.2 s`，即 5 Hz。规划器同时发布：

```text
/global_planner/obstacles_raw
/global_planner/obstacles_inflated
```

两者都是 `nav_msgs/OccupancyGrid`，可在 RViz 中直接比较楼间通道是被原始点云封闭，还是被安全膨胀封闭。

### 4.5 A* 搜索、路径抽稀和子目标跟踪

全局搜索使用 8 邻接 A*：

- 水平/垂直移动代价为一个栅格边长；
- 对角移动代价为 `sqrt(2)` 个栅格边长；
- 启发函数为到目标的欧氏距离，因此对当前长度/净空代价仍保持最优 A*；
- 禁止从两个接触的障碍角之间对角穿过；
- 若起点落入新出现的安全膨胀区，在 `3 m` 内选择真实欧氏最近的自由 cell；
- 若目标落入膨胀区，只在“与起点同一可达连通域”内寻找 `3 m` 内最近自由 cell，避免把目标错误投到楼的另一侧。

规划前先做 supercover 直线碰撞检查。如果起点到目标满足 `1.0 m` 硬净空，就直接采用欧氏最短直线，不再让软代价产生绕路。只有直线被阻挡时才运行 A*。A* 原始路径随后经过同样的 supercover 视线检查做 string-pulling，只保留必要转折点，而且不允许从障碍角点缝隙中穿过。

执行路径时采用“萝卜点”前瞻：

- 到当前路点 `1.5 m` 内认为该路点已到达；
- 沿安全全局折线向前计算 `7.0 m`；
- 如果下一个转折点超过 7 m，就在已经验证无碰的线段中插值出精确前瞻点；
- 将该前瞻点作为 `/goal_elevated` 发给 EGO；
- 子目标变化不足 `1.0 m` 且高度变化不足 `0.5 m` 时不重复触发 EGO 重规划；
- 子目标距 UAV 小于 `0.8 m` 时不发送，避免 EGO 收到 `start≈goal` 的退化目标后卡在重规划状态；
- 到最终目标 `1.5 m` 内后清空路径，停止发新子目标，UAV 悬停等待下一目标。
- 每次地图快照更新都会重新计算候选路径；新路径至少缩短 5% 或旧路径已被堵塞时才替换，兼顾最短路与轨迹稳定性。

如果 A* 找不到安全连通路径，当前默认不再把最终目标直接穿过障碍发给 EGO，而是保留悬停并等待下一张地图快照或新目标。只有显式设置 `allow_unsafe_goal_fallback=true` 才会恢复旧的不安全直发行为，正式排雷不应开启。

### 4.6 巡航高度如何计算

低空模式并非始终使用绝对 `z=4 m`。全局规划器对每个子目标估计沿途地面最高值：

```text
z_target = max(max_ground_along_path + flight_height, min_subgoal_z)
```

默认：

```text
flight_height = 4.0 m
min_subgoal_z = 2.0 m
```

沿当前点到萝卜点逐段查询地面，使用沿途最高地面而不是只看终点地面，可以避免飞向下坡目标时过早降低高度并撞到当前高地。每个 5 Hz tick 的高度变化最多 `0.6 m`，避免目标高度瞬跳。

高空模式默认使用：

```text
flight_height = 12.0 m
max_vel = 1.5 m/s
```

低空模式默认使用：

```text
flight_height = 4.0 m
max_vel = 1.2 m/s
```

### 4.7 前视深度如何进入 EGO

原始前视深度图为：

```text
/iris_depth_camera/camera/depth/image_raw
```

`depth_preprocess_node` 执行：

1. 将 NaN、零值、小于 `0.25 m` 或大于 `15 m` 的无效深度设为 `15 m`；
2. 使用 `7×7` 椭圆核对深度图做腐蚀；
3. 深度越小表示障碍越近，所以腐蚀操作会把近障碍向图像周围扩张；
4. 将输出统一转换为毫米单位的 `16UC1`；
5. 最近邻缩放到 `640×360`；
6. 发布到 `/depth/image_dilated`。

EGO 使用的相机参数为：

```text
cx=320.0, cy=180.0
fx=343.158, fy=343.158
depth range=0.25～15.0 m
skip_pixel=2
```

EGO 局部占据图和轨迹参数为：

| 参数 | 当前值 | 作用 |
|---|---:|---|
| 地图分辨率 | 0.3 m | 三维占据栅格分辨率 |
| 地图范围 | 200×200×15 m | 规划固定地图边界 |
| 低空局部更新范围 XY | 15 m | 提前把前方建筑加入局部地图 |
| 局部更新范围 Z | 2.5 m | 垂直局部更新范围 |
| 障碍膨胀 | 0.24 m | 占据图安全边界 |
| 优化安全距离 `dist0` | 0.4 m | B 样条远离障碍的目标距离 |
| 规划时域 | 8.0 m | 局部规划前瞻范围 |
| 最大速度 | 低空 1.2 m/s | 由启动参数传入 |
| 最大加速度 | 1.0 m/s² | 防止急加减速和点云拖影 |
| 最大 jerk | 4 | 轨迹动力学约束 |

EGO 从深度图更新概率占据栅格，再对轨迹控制点进行平滑性、碰撞、可行性和目标贴合优化，最后由 `traj_server` 发布：

```text
/planning/pos_cmd
```

### 4.8 PX4 Bridge 如何执行并保证基本安全

`px4_bridge.py` 的启动和执行顺序为：

1. 等待 `/mavros/state` 连接；
2. 等待 `/mavros/local_position/pose`；
3. 先连续发送 100 个起飞位置设定值，满足 PX4 进入 OFFBOARD 前必须已有 setpoint 流的要求；
4. 反复请求 `OFFBOARD` 和解锁，直到 MAVROS 状态确认；
5. 起飞到 `2.5 m`；
6. 高度达到 `1.5 m` 后才允许 EGO 指令接管；
7. 将 `/planning/pos_cmd` 转成 `/mavros/setpoint_position/local`；
8. 以 `50 Hz` 持续发送位置 setpoint；
9. EGO 指令超过 `1.5 s` 未更新时，改为保持当前位置；
10. 对所有规划高度施加 `z≥0.8 m` 下限。

Bridge 内还有前视深度紧急拦截逻辑，但当前：

```text
ENABLE_DEPTH_INTERCEPT=False
```

即默认完全由全局 A* 和 EGO 规划避障，Bridge 不再因为近障反复抢控制。若以后启用，中心小于 `0.65 m` 会强制悬停，前方区域小于 `1.35 m` 会拦截继续前冲；启用前必须重新验证它不会和 EGO 产生前进—悬停振荡。

## 5. UAV LiDAR 建图与地图转换

### 5.1 建图不是一个节点，而是四个阶段

```text
阶段 1：Gazebo 原始 PointCloud
    /uav0/velodyne_points_raw

阶段 2：传感器系过滤后 PointCloud2
    /uav0/mapping/velodyne_points_sensor

阶段 3：固定坐标系单帧点云
    /uav0/mapping/points_world

阶段 4：固定坐标系累积点云和 PCD
    /uav0/mapping/points_accumulated
    ~/pointcloud_maps/uav_points_map_latest.pcd
```

这四个话题的用途不同：

- `points_raw` 只表示当前扫描，格式还是旧的 `sensor_msgs/PointCloud`；
- `velodyne_points_sensor` 已经过滤，但坐标仍相对 LiDAR；
- `points_world` 是当前帧投影后的固定系点云；
- `points_accumulated` 才是边飞边长大的全局地图。

### 5.2 原始 LiDAR 参数

地雷版 UAV 的 LiDAR 参数为：

```text
水平采样：360
垂直线数：16
水平视场：-π ～ +π
垂直视场：-30° ～ +30°
更新率：3 Hz
量程：0.3 ～ 16.0 m
分辨率：0.01 m
原始话题：/uav0/velodyne_points_raw
原始 frame：uav0/velodyne_link
```

### 5.3 阶段一：格式转换和传感器系过滤

`pointcloud_to_pointcloud2_relay.py` 将 Gazebo block laser 发布的 `PointCloud` 转成 `PointCloud2`，并在转换前完成以下过滤。

#### 机体自滤波

过滤器删除 UAV 自身机体和旋翼回波：

- 机体圆柱半径 `0.28 m`，局部 z 范围 `[-0.16, 0.16] m`；
- 四个旋翼中心按 Iris 几何给定；
- 旋翼过滤半径 `0.17 m`，相对旋翼中心 z 范围 `[-0.14, 0.06] m`。

如果不做这一步，累积图中会沿 UAV 航迹形成一串“飞行器自身障碍”。

#### 距离过滤

合并启动配置实际使用：

```text
min_range = 0.35 m
max_range = 15.0 m
sensor_max_range = 16.0 m
max_range_margin = 0.8 m
```

因此过近点、15 m 外点以及接近 16 m 最大量程的无返回边界点会被删除，避免地图外围出现一圈假的最大量程墙。

#### 稀疏离群点过滤

当前配置：

```text
neighbor_voxel_size = 0.16 m
min_neighbors = 2
relay_voxel_size = 0.06 m
```

对每个点统计其所在邻域 `3×3×3` 体素中的点数，邻居不足 2 的孤立点被删除。保留下来的点再以 `0.06 m` 体素降采样，每个体素保留距离传感器较近的点。

#### 运动门控

过滤器支持根据 IMU 和里程计速度丢弃高速扫描，以降低运动拖影。合并世界当前为保证持续建图，限制已经放宽：

```text
max_linear_velocity = 3.0 m/s
max_odom_angular_velocity = 0（真值投影模式下关闭）
max_odom_age = 999 s（真值投影模式下关闭时效门）
```

正常 TF/MAVROS 投影模式下会重新启用里程计时间和角速度检查。状态日志会分别统计 `old_odom`、`linear`、`odom_ang` 等丢帧原因。

### 5.4 阶段二：点云从 LiDAR 坐标转换到固定坐标

项目有两种投影实现，不能混为一谈。

#### 路径 A：TF 投影，适用于正常系统和真机

节点：

```text
uav_pointcloud_to_world.py
```

它查询：

```text
T_map_lidar(t)
```

然后对当前帧每个点执行：

```text
p_map = T_map_lidar(t) · p_lidar
```

正常情况下使用点云时间戳 `t` 查询 TF。如果发生 TF extrapolation 且允许 fallback，代码会尝试最新 TF。

最新 TF 回退只能作为点云不断流的容错。UAV 运动时会产生近似误差：

```text
position_error ≈ linear_velocity × |Δt|
```

还会叠加角速度导致的旋转误差。因此实机建图应优先修好时间同步，尽量使用扫描时刻 TF；不能把 `force_latest_tf` 当成高精度定位方案。

转换后节点会再次按传感器原点计算距离，删除最大量程边界，并可做固定系体素降采样。

#### 路径 B：Gazebo 真值投影，只适用于仿真

节点：

```text
uav_truth_cloud_projector.py
```

当前 `run_air_ground.sh` 设置：

```text
use_truth_tf:=true
```

所以合并仿真实际使用 Gazebo `/gazebo/model_states` 中的 UAV 当前真值位姿，绕开重负载仿真中可能冻结的 MAVROS TF 和时间戳：

```text
p_output = P_truth + R_truth · (p_lidar + p_mount) - p_offset
```

其中：

- `P_truth, R_truth` 为 Gazebo 中 UAV 的位置和姿态；
- `p_mount=(0,0,0.06)` 为 LiDAR 安装偏移；
- `p_offset=(UAV_X,UAV_Y,0)` 时，输出落在 MAVROS 局部坐标；
- `p_offset=0` 时，输出直接是 Gazebo 世界坐标。

该节点故意使用最新真值位姿，不按点云时间戳插值。它解决仿真卡顿导致“所有点云只堆在一个圆里”的问题，但仍可能有小量最新位姿—扫描时刻拖影，所以当前低空速度限制为 `1.2 m/s`。

这条真值路径不能用于实机，也不能作为论文中真实定位性能的依据。

### 5.5 阶段三：体素累积、重复观测和射线清障

节点：

```text
uav_pointcloud_map_recorder.py
```

当前合并配置的主要参数为：

```text
voxel_leaf_size = 0.10 m
min_observations = 1
publish_rate = 2.0 Hz
save_interval = 30.0 s
ground_filter_mode = none
ray_clearing_enabled = true
```

每个固定系点先映射到三维体素键：

```text
key = floor([x,y,z] / voxel_leaf_size)
```

每个体素保存：

- 所有点的 `x/y/z` 累加和；
- 总样本数；
- 来自多少个不同扫描帧；
- 最后一次观察帧号。

发布时用该体素所有样本的平均位置作为输出。`min_observations=1` 表示单次飞过的区域也进入地图；如果改成 3，则同一体素至少要被三个不同扫描帧看到，噪声更少，但单程覆盖区域可能缺失。

射线清障从 LiDAR 原点向每个终点采样：

```text
有效射线距离：0.5～15.0 m
采样步长：0.20 m
每 8 个终点处理一个
终点前保留 3 个体素，不当作自由空间删除
```

射线中间经过的旧占据体素会被删除，用于消除姿态抖动或动态回波留下的幽灵点。若查询不到 `map <- uav0/velodyne_link`，该帧仍会记录终点，只跳过射线清障。

累积输出为：

```text
/uav0/mapping/points_accumulated
```

保存服务为：

```bash
rosservice call /uav_pointcloud_map_recorder/save
```

默认生成：

```text
~/pointcloud_maps/uav_points_map_latest.pcd
~/pointcloud_maps/uav_points_map_YYYYmmdd_HHMMSS.pcd
```

### 5.6 为什么累积地图保留地面点

当前：

```text
map_ground_filter_mode = none
```

这不是漏做地面过滤。UAV 交给后续地形转换的地图需要保留地面高度，才能计算 DEM、坡面和高出地面的结构。如果在 UAV 累积阶段直接删除所有地面点，后面只能得到障碍点，无法判断缓坡和可通行地面。

### 5.7 三维点云如何转换为公共二维地形地图

地图交付边界使用：

```text
src/mobile_manipulator/scripts/pcd_to_occupancy_map.py
```

它可以处理两种输入：

```text
在线：/uav0/mapping/points_accumulated
离线：~/pointcloud_maps/uav_points_map_latest.pcd
```

在线模式默认每 `3 s` 重建一次地形图。转换步骤为：

1. 按 `0.25 m` 分辨率划分 XY 栅格；
2. 删除全局极低离群点；
3. 在每个 cell 内根据 z 均值和标准差去掉明显偏低噪声；
4. 取每个 cell 最低有效 z 作为地面候选；
5. 对无数据空洞使用最近邻地面填充；
6. 使用约 `2.0 m` 中值窗口得到平滑 DEM；
7. 从 DEM 梯度计算坡度，坡度主要用于显示和可选软代价；
8. 统计高出本地地面超过 `0.4 m` 的结构点；
9. 同一 cell 至少有 3 个结构点时标为致命障碍 `100`；
10. 有地面数据的 cell 为可通行 `0`，UAV 未覆盖区域为未知 `-1`；
11. 只删除点数不足且完全孤立的致命噪声格，保留路灯、树干等细障碍。

输出包括：

```text
/terrain_map     nav_msgs/OccupancyGrid
/terrain_slope   nav_msgs/OccupancyGrid
/terrain_cloud   sensor_msgs/PointCloud2
```

此处只是把 UAV 地图转换成统一产品；本文不继续展开 UGV 如何配置 costmap 或如何跟踪路径。

## 6. 坐标对齐：建图和地雷定位共用的核心

### 6.1 需要对齐的不是一个坐标，而是三条数据链

以下数据必须最终落在同一个公共 `map`：

1. UAV LiDAR 累积点云；
2. UAV 下视相机识别出的地雷位置；
3. UGV 自身定位和接收目标时使用的地图。

如果只把 RViz 画面对齐，而消息中的数值没有对齐，UGV 仍会驶向错误位置。

### 6.2 当前默认仿真为什么天然重合

当前 `run_air_ground.sh` 默认：

```text
UAV_X=0
UAV_Y=0
Gazebo world 原点 = UAV 出生点 = MAVROS local 原点
```

所以：

```text
p_world = p_local
```

这时无论规划目标、点云还是地雷位置，数值上都不需要平移。它只是零偏移的特殊情况，不代表系统在任意出生位置都自动对齐。

### 6.3 非零出生点时的平移关系

若 UAV 在 Gazebo 世界中的出生点为：

```text
o = [UAV_X, UAV_Y, 0]
```

MAVROS local 中 UAV 起点约为零，则：

```text
p_map = p_uav_local + o
p_uav_local = p_map - o
```

这个关系在三个位置使用：

- 公共目标交给 UAV 规划器时减 `o`；
- UAV 局部点云交付公共地图时加 `o`；
- UAV 局部系地雷坐标交给 UGV 前加 `o`。

如果只修正点云而没有修正地雷，RViz 地图会看起来正确，但 UGV 收到的雷点仍会整体偏移；反过来也一样。

### 6.4 当前仿真真值 TF 路径

合并仿真中 `gazebo_uav_marker.py` 可根据 `/gazebo/model_states` 发布：

```text
map -> uav_base_link
```

其平移实际计算为：

```text
t = P_gazebo_truth - [UAV_X, UAV_Y, ref_z]
```

这样 TF 数值位于 MAVROS 局部坐标。LiDAR 真值投影器也会减去同一个出生点偏移，因此 EGO、全局 A* 和点云内部使用同一局部数值。

需要特别说明：当前代码仍把这个内部局部结果的 `frame_id` 写成 `map`。默认 `UAV_X=UAV_Y=0` 时没有问题；非零出生点时容易混淆“名为 map 的局部值”和“真正公共 map 值”。更干净的长期方案是新增明确的 `uav_local` 帧：

```text
map -> uav_local                 固定出生点变换
uav_local -> uav_base_link       MAVROS/真值动态位姿
uav_base_link -> sensors         静态外参
```

这样任何带 `frame_id=map` 的地图或地雷消息都必须已经完成公共坐标转换。

### 6.5 正常 MAVROS/TF 路径

不用 Gazebo 真值时，`mavros_tf_bridge.py` 从：

```text
/mavros/local_position/odom
```

发布 UAV 基座动态 TF。完整 LiDAR 链应为：

```text
map 或 uav_local
  └── uav_base_link
        └── uav0/velodyne_link
```

完整地雷相机链应为：

```text
map 或 uav_local
  └── uav_base_link
        └── mine_camera_optical_frame
```

在实机中必须使用这类估计位姿链，而不是 `/gazebo/model_states`。如果 UAV 使用 VIO、SLAM 或 GNSS/INS，应由定位系统提供稳定的 `map/odom -> base_link` 变换。

### 6.6 在线仿真地图自动平移

`pcd_to_occupancy_map.py` 支持仿真在线自动计算：

```text
offset_xy = GazeboTruth_UAV_xy - MAVROSLocal_UAV_xy
```

然后：

```text
p_map_xy = p_cloud_xy + offset_xy
```

这只估计二维平移，不估计 yaw 旋转。它依赖 Gazebo 真值，只适合仿真验证。

当前 `run_air_ground.sh` 因为 UAV 默认出生在 `(0,0)`，给地形转换传的是显式 `align_offset_x/y=UAV_X/UAV_Y`，并关闭该消费者内部的 `auto_align`。因此当前主路径依赖已知出生点，而不是在线 truth-minus-odom。

### 6.7 离线 PCD 的 GPS/UTM 对齐

`uav_map_origin_saver.py` 同时接收：

```text
/mavros/global_position/global
/mavros/local_position/odom
```

MAVROS local ENU 中 `x` 为东、`y` 为北。当前时刻 GPS 转成 UTM 后，反推 UAV 局部地图原点：

```text
UAV_origin_E = UTM(current_GPS).E - local_x
UAV_origin_N = UTM(current_GPS).N - local_y
```

结果每 2 秒写入：

```text
~/pointcloud_maps/uav_map_origin.yaml
```

当前保存器使用最近收到的 GPS 和 odom，并没有对两条消息做严格时间同步。仿真低速时通常足够；实机或高速飞行时应按时间戳同步，或者把 GPS 插值到 odom 时刻，否则两条消息的时间差也会进入原点平移误差。

离线读取 PCD 时，再用公共 datum 的 UTM 坐标计算：

```text
offset_x = UAV_origin_E - datum_E
offset_y = UAV_origin_N - datum_N
p_map = p_pcd + [offset_x, offset_y, 0]
```

必须保证 UAV 原点和 datum 位于同一个 UTM zone。当前实现只校正平移；若实机地图 XY 轴没有与 ENU 东北方向对齐，还需要使用至少两个公共控制点或 GNSS 航向估计二维旋转：

```text
p_map_xy = R(yaw_offset) · p_local_xy + t_xy
```

### 6.8 地雷定位为什么必须使用图像时刻 TF

地雷很小，地雷位置对时间误差比普通环境点云更敏感。对一张时间戳为 `t_img` 的 RGB/深度观测，必须查询：

```text
T_map_camera(t_img)
```

不能直接用收到消息时的最新 UAV 位姿。若 UAV 速度为 `v`、图像和位姿相差 `Δt`，仅平移误差就约为：

```text
e_time ≈ v · |Δt|
```

例如 `v=1.2 m/s`、`Δt=0.1 s`，会产生约 `0.12 m` 平移误差，已经可能显著影响 UGV 的接近位置。还未计算 UAV 姿态变化造成的地面投影误差。

因此地雷在线节点应：

- RGB 和深度做时间同步；
- 使用 RGB/深度共同观测时间；
- 严格查询该时刻的 `map <- mine_camera_optical_frame`；
- TF 不可用时丢弃本帧，不能为了“不断流”默认使用 latest TF；
- 在消息中保留原始观测时间、定位协方差和 TF 是否精确匹配的诊断信息。

### 6.9 坐标对齐检查命令

检查 TF 是否完整：

```bash
rosrun tf tf_echo map uav_base_link
rosrun tf tf_echo uav_base_link uav0/velodyne_link
rosrun tf tf_echo uav_base_link mine_camera_optical_frame
```

检查 UAV 位姿、点云帧名和时间戳：

```bash
rostopic echo -n1 /mavros/local_position/odom/header
rostopic echo -n1 /uav0/mapping/points_world/header
rostopic echo -n1 /uav0/mapping/points_accumulated/header
```

非零出生点时，在同一时刻记录：

```text
Gazebo UAV world position
MAVROS UAV local position
两者之差
```

该差值应长期接近 `[UAV_X,UAV_Y]`，不能随飞行明显变化。

## 8. UAV 在线地雷识别与 map 坐标计算

本节对应的在线链路已经实现，入口为 `launch/mine_detection.launch`。

实现节点：

```text
mine_seg_localizer_node.py
```

### 8.1 输入和输出

输入：

```text
/mine_camera/rgb/image_raw
/mine_camera/depth/image_raw
/mine_camera/rgb/camera_info
/tf
best.pt 或 best.onnx
```

单帧输出建议为：

```text
/mine_detection/raw          每帧实例的 map 坐标、置信度、深度和 mask 面积
/mine_detection/debug_image  叠加掩膜、置信度和 map 坐标的调试图
/mine_detection/inference_ms CPU 推理耗时
```

融合后输出建议为：

```text
/mine_detection/map          候选和已确认目标，类型 MineMap
/mine_detection/confirmed    只含已确认坐标，类型 PoseArray，供 UGV 使用
/mine_detection/markers      RViz 中候选/确认地雷和 ID
/mine_detection/map_json     可跨语言读取的 JSON 镜像
mine_detection_output/mine_map.yaml
```

### 8.2 RGB、深度和相机内参同步

RGB 和深度应使用 `message_filters.ApproximateTimeSynchronizer`，队列可从 8 开始，允许时间差建议先设为 `0.03～0.08 s`，再根据实际话题时间戳统计调整。

处理一帧前必须满足：

- RGB 和深度尺寸一致，或已用明确标定关系对齐；
- CameraInfo 的 `K` 矩阵有效；
- RGB 和深度时间差不超过设定阈值；
- 可以查询图像时刻的相机到公共地图 TF；
- 深度单位已统一为米：`16UC1` 乘 `0.001`，`32FC1` 直接使用。

### 8.3 实例分割而不是矩形框深度

现有 `target_yolo_detector_node.py` 使用目标框中心和框内深度百分位，适合较大的空中目标代码复用，但不能原样用于小地雷。地雷节点应使用 `result.masks`：

1. 只保留类别 `landmine`；
2. 置信度低于阈值的实例删除；
3. 将模型输出 mask 恢复到原始 960×540 尺寸；
4. 删除面积过小、贴图像边界严重或形状异常的 mask；
5. 每个实例独立计算深度和三维位置。

使用实例掩膜可以避免矩形框内大量地面、草和阴影深度污染地雷距离。

### 8.4 掩膜内鲁棒深度

建议对每个 mask 执行：

1. 向内腐蚀 2～3 像素，减少分割边界混入背景；
2. 取腐蚀后 mask 内有限且位于 `[0.1,20] m` 的深度；
3. 有效深度点少于最小数量时拒绝；
4. 计算深度中位数 `z_med`；
5. 计算 `MAD = median(|z-z_med|)`；
6. 只保留满足下式的点：

```text
|z-z_med| ≤ max(0.03 m, 3 × 1.4826 × MAD)
```

7. 若保留比例太低或深度离散度过大，拒绝该观测。

中位数和 MAD 对地面边缘、深度空洞及少量异常点比均值更稳健。

### 8.5 像素反投影到相机三维坐标

从 CameraInfo 读取：

```text
fx = K[0]
fy = K[4]
cx = K[2]
cy = K[5]
```

对掩膜内有效像素 `(u,v)` 和深度 `z`：

```text
x_cam = (u-cx) × z / fx
y_cam = (v-cy) × z / fy
z_cam = z
```

得到：

```text
p_cam = [x_cam, y_cam, z_cam, 1]^T
```

这里使用的是 ROS 光学坐标约定，不是 UAV 机体坐标约定。

对小地雷，推荐把多个有效 mask 像素分别反投影，再对 map 中的 `x/y/z` 取鲁棒中位数；比“只取 mask 中心像素 + 一个深度”更不容易受中心深度空洞影响。

### 8.6 从相机坐标变换到公共 map

在图像时间 `t` 查询：

```text
T_map_camera(t)
```

然后：

```text
p_map = T_map_camera(t) · p_cam
```

该矩阵包含两部分：

```text
T_map_camera(t) = T_map_uav(t) · T_uav_camera
```

- `T_map_uav(t)` 来自 UAV 定位；
- `T_uav_camera` 来自固定安装外参；
- 仿真中可用真值验证，但最终算法应使用与实机一致的估计位姿链。

如果当前仿真 TF 中的 `map` 实际仍表示 MAVROS local，且 UAV 出生点非零，还要执行：

```text
p_common_map = p_tf_result + [UAV_X,UAV_Y,0]
```

然后才能发布给 UGV。默认出生点为零时两者相同。

### 8.7 单帧观测拒绝条件

满足任一条件就不应生成有效地雷坐标：

- 分割置信度过低；
- mask 面积过小或大部分在图像外；
- 有效深度点太少；
- 深度 MAD 过大；
- RGB 与深度时间差过大；
- 图像时刻 TF 不可用；
- 反投影结果在相机后方或超出合理飞行高度/视距；
- 估计点与当前地面高度严重不一致；
- UAV 翻滚/俯仰过大，地面投影误差超过阈值；
- 同一实例的三维点云横向范围明显大于真实地雷尺寸。

拒绝帧必须发布诊断原因，例如：

```text
no_mask
low_confidence
insufficient_depth
depth_inconsistent
rgb_depth_unsynced
exact_tf_unavailable
projection_out_of_range
```

当前 `mine_map_fusion_node.py` 还提供可配置的公共地图高度门控：

```text
min_map_z <= detection.position.z <= max_map_z
```

通用 launch 默认放宽，不假定地形海拔；`run_air_ground.sh` 针对当前道路雷场设为 `-0.10～0.15 m`。第一轮端到端测试曾出现一个 `z≈0.29 m` 的离地物体被连续误判，该门控在第二轮过滤了这类明显不贴地的确认级误报。换到起伏地形或真机前必须依据公共地图地面高程调整，不能机械沿用绝对 z 门限。

### 8.8 位置协方差

每个单帧观测不能只发布 `(x,y,z)`，还要给出位置不确定度。主要误差包括：

```text
分割像素误差
深度噪声
相机内参误差
相机外参误差
UAV 位姿误差
RGB/深度/位姿时间误差
```

初版可以根据掩膜内反投影点在 map 中的离散度估计测量协方差，再叠加 UAV 位姿协方差和最小噪声下限。至少发布 `x/y/z` 三个方差，不能用固定置信度代替几何误差。

## 9. UAV 地雷语义地图和多帧融合

单帧检测不能直接交给 UGV。UAV 飞过同一地雷时会连续看到多次；如果每帧都当新目标，UGV 会收到大量重复雷点。

当前实现节点：

```text
mine_map_fusion_node.py
```

### 9.1 数据关联

对每个新观测 `z`，在已有地雷轨迹中查找候选：

- 先用 XY 欧氏距离门限，例如 `0.5 m`；
- 再使用观测和轨迹协方差计算 Mahalanobis 距离；
- 选择距离最小且通过门限的目标；
- 无候选时创建新目标。

不能仅按 YOLO 实例序号关联，因为实例序号每帧都会变化。

### 9.2 融合

若已有目标均值和协方差为 `(μ,P)`，新观测为 `(z,R)`，可以用信息形式融合：

```text
P_new = (P^-1 + R^-1)^-1
μ_new = P_new(P^-1 μ + R^-1 z)
```

也可以使用静态目标卡尔曼滤波。地雷在地图中不运动，状态只需要位置和必要的类别/置信度信息，不需要速度状态。

### 9.3 确认和去重

建议状态为：

```text
TENTATIVE   刚检测到，不能派发
CONFIRMED   多帧一致，可以交给 UGV
REJECTED    后续观测不支持或被判为误报
CLEARED     UGV 完成处理后回写，仅作为共享状态
```

一个目标进入 `CONFIRMED` 的初始条件可以设为：

- 至少 3 次有效观测；
- 观测来自至少两个不同时间或不同 UAV 位姿；
- 融合后 XY 标准差低于设定阈值；
- 平均分割置信度达到阈值；
- 目标没有与已有确认目标重复。

这些阈值必须通过仿真真值误差统计确定，不能只凭一次视觉效果决定。

### 9.4 保存到地图中的含义

“把地雷保存到图中”不应直接把地雷 cell 写成普通障碍并丢失属性。环境栅格和地雷语义层应分开：

```text
环境层：/terrain_map
语义层：/mine_detection/map
UGV 交付层：/mine_detection/confirmed
显示层：/mine_detection/markers
持久化：mine_map.yaml 或 mine_map.json
```

持久化记录至少包括：

```yaml
frame_id: map
targets:
  - id: mine_0001
    position: [12.34, -5.67, 0.08]
    covariance_xy: [0.02, 0.00, 0.00, 0.03]
    confidence: 0.91
    observations: 6
    status: CONFIRMED
    first_seen: 123.4
    last_seen: 128.7
```

这样 UAV 地图既能保存环境几何，又能保存地雷 ID、置信度、不确定度和任务状态。

## 13. 常见问题定位

### 13.1 UAV 能飞但不会绕大楼

按顺序检查：

```text
/uav0/mapping/points_accumulated 是否有点
global_path_planner 是否打印已扫 cell
/global_path 是否生成
大楼是否满足相对地面高度和 10m² 连通域门限
目标是否被正确从 map 减去出生点偏移
```

### 13.2 全局路径正确但 UAV 仍撞局部障碍

检查：

```text
/depth/image_dilated 是否持续更新
深度图 frame、尺寸和 16UC1 单位是否正确
EGO 的 map/pose/depth 输入时间是否正常
障碍是否在前视相机视场之外
max_vel 是否过大
```

全局 A* 会主动过滤小于 10m² 的障碍，这些障碍必须由 EGO 看见并避开。

如果路径不必要地绕远，先在 RViz 对比：

```text
/global_planner/obstacles_raw
/global_planner/obstacles_inflated
```

- 原始图已经封住通道：检查累积点云拖影、射线清障和 TF；
- 原始图通、膨胀图不通：通道无法满足当前 1.0 m 全局硬净空；
- 膨胀图也通但路径仍绕：检查目标是否落在公共 map 范围内，并查看规划日志中的 `projected` 和路径长度。

### 13.3 点云只堆在一个位置

检查投影日志中的：

```text
proj TF map<-uav0/velodyne_link = (...)
```

如果 UAV 已经飞行但该位置不变，说明动态 TF 冻结。仿真可检查 `/gazebo/model_states` 和真值投影器；实机必须修复定位/TF 时间链，不能依赖 Gazebo 真值。

### 13.4 地图整体平移

最常见原因是把 MAVROS local 当成公共 map。检查：

```text
UAV_X/UAV_Y
truth_xy - mavros_xy
地形转换 offset_x/offset_y
PCD sidecar 中的 UTM 原点
```

点云、地雷和目标三条链必须使用同一个偏移方向：局部转公共时加，公共目标转局部规划时减。

### 13.5 地雷标记随 UAV 一起移动

这通常说明发布的是相机或机体系坐标，却错误标成了 `map`。检查输出数值是否真正执行：

```text
p_map = T_map_camera(t_img) · p_camera
```

已发布的历史地雷点应固定在地面，不应随 UAV 后续运动改变。

### 13.6 地雷坐标固定偏一个方向

检查：

- `uav_base_link -> mine_camera_optical_frame` 的平移和旋转；
- 下视光学 `+Z` 是否真的指向地面；
- `fx/fy/cx/cy` 是否来自同一分辨率的 CameraInfo；
- UAV 非零出生点偏移是否在交付前加回；
- RGB、深度和 TF 是否使用同一个观测时间。

## 15. UAV 后续实现顺序

下视载荷、模型、同步深度定位、图像时刻 TF、多帧确认、YAML 持久化、一键启动和 Gazebo 真值评分均已完成。下一阶段按下面顺序推进：

1. 让 UGV 任务管理器订阅 `/mine_detection/confirmed`，逐个领取目标；
2. 增加 `ASSIGNED / CLEARED` 等任务状态及 UGV 回写服务；
3. 在更多建筑阴影、草地和不同高度航线中重复五目标回归测试；
4. 若转入真实硬件，先采集真实下视相机数据微调模型，再重新标定相机外参和时间同步；
5. 最后接入 UGV 末端探测与机械臂排雷动作。

这样划分后，UAV 模块的验收边界非常明确：UAV 必须交付一个坐标正确、可重复加载的环境地图，以及一组位于同一公共 `map` 中、带稳定 ID 和不确定度的已确认地雷目标。
